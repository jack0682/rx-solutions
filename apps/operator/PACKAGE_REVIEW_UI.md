# 반입·검토·소프트웨어 승인 화면

2026-09-12. 기존 운영 앱에 `패키지 검토`를 추가했다. Engineer/Verifier가 허용된 셀의 반입 기록과 검토 요청, 원문·컴파일 결과·검증 근거를 확인한다. 이 화면에서 운전 활성화를 수행하지 않는다.

## 화면 흐름

1. **반입 기록**: Engineer가 서버 반입 폴더의 상대 경로, 내용/서명 식별자와 제목으로 반입한다. 현재 구현은 준비된 서버 파일을 사용하며 브라우저 파일 업로드를 흉내 내지 않는다.
2. **새 검토 요청**: 패키지의 operation 이름을 현재 셀의 정확한 장비 작업에 연결한다. 검증 서명자 구성이 없으면 생성을 활성화하지 않는다. 요청 JSON은 S 검증 도구에 전달할 수 있도록 내려받는다.
3. **검증 자료**: 외부 도구·서명자가 만든 자료 폴더와 보고서 digest를 등록한다. P가 검증한 결과·issue·서명자·검토 식별자를 표시한다.
4. **검토**: 공정 원문의 흐름을 제한된 행으로 보여주고, 전체 원문/조건·compiled 결과·현재 셀 snapshot/선택/검증 근거를 펼쳐 확인하거나 내려받는다. 긴 원문은 전체 JSON/다운로드로 확인한다. 요약 화면이 모든 공정 의미를 검증했다고 표시하지 않는다.
5. **결정**: 현재 Verifier만 승인/반려할 수 있다. 제출 계정의 승인은 비활성화한다. 원문/결과/셀 연결과 버전을 확인한 뒤 의견을 적고, 대상 제목·revision·전체 review digest가 있는 창에서 기록한다.

반입/검토 목록은 ID cursor로 다음 페이지를 조회한다. 각 반입 건의 검토 요청만 목록에 표시한다. 과거 검증 revision은 읽기 전용으로 표시하고, 현재 검증 revision과 구별한다. 과거 화면에서 승인이나 새 보고서를 등록하지 않는다. Backend도 항상 최신 검토 revision과 CAS를 확인한다.

## 현재성과 응답 유실

- 선택된 자료는 활성 화면에서 약3초마다 재조회한다. 마지막 조회 시작으로부터10초가 지났거나 오류가 있으면 새 조작을 막는다. 이는 장비 상태의 실시간 보장이 아니다.
- 원문·결과·구성·검증/결정 metadata를 포함한 표시 자료의 snapshot으로 확인 표시를 묶는다. 재조회로 snapshot이 달라지면 확인 표시와 열린 승인 창을 해제한다.
- 창에서 확정하는 시점에도 현재 snapshot·revision·digest·계정 역할·최신 여부를 대조한다. server가 마지막 권한과 정책/내용을 다시 검사한다.
- 반입·검토 생성·보고서·결정은 기존 전역 pending 요청 저장소를 재사용한다. 전송 전에 같은 key/body/계정/설치/store generation을 sessionStorage에 남긴다.
- 처리 중과 결과 미확인 문구를 구별한다. 결과가 불명일 때 새 요청을 만들지 않고 기존 요청 번호와 내용으로 회수한다. 새로고침 후에도 유지한다. 다른 계정/설치에서 회수하지 않는다.
- 응답은 대상 셀·ID·검토 digest·revision·의견/choice 등 원래 요청과 일치해야 한다. 잘못된 응답을 받으면 성공으로 지우지 않는다. Counter는 BigInt로 비교한다.
- 과거 결정이 조회되어도 현재 검토에 적용되는지 별도로 표시한다. `소프트웨어 승인 기록`은 운전 자격이나 장비 준비 표시가 아니다.

화면 입력/선택은 현재 계정·설치·셀별 메모리에 보관한다. 페이지 전체 새로고침 시 미전송 일반 폼은 복원하지 않으며, 전송한 pending 요청은 복원한다. 로그인 계정이나 설치가 바뀌면 편집 context를 분리한다.

## API 보완

P에 `GET /api/v1/process-reviews?cell=...&intake=...&after=...`와 단일 검토 조회의 선택 `revision`을 추가했다. 현재 반입 context는 review authority 설정의 존재도 알려준다. 역사 자료를 조회해도 승인 엔드포인트가 사용하는 최신 revision 기준은 바꾸지 않았다.

현재 목록은 기존 document repository의 scan을 사용한다. 출력 페이지 크기는50개이며, 대규모 장기 보관용 DB 인덱스/서버 paging 최적화는 후속이다.

## 검증과 배포 경계

단위 검사는 별도 검토자·현재성/역사 guard, 자료 변경에 따른 확인 stamp, 요청/응답 일치와 큰 정수 revision을 다룬다. 새 브라우저 시험은 실제 P API와 별도 S 컴파일러를 사용하고 test-only 서명자로 만든 자료를 제출한다. 반입·작업 연결·request export·보고서 등록·self-approval 거부·새 revision의 확인/창 해제·과거 읽기·응답 유실 후 재시작/동일 key 회수와 모바일 화면을 확인한다.

브라우저용 로컬 개발 서비스에는 명시적 private `package-service.json`을 사용할 수 있다. 기존 production daemon의 mTLS 설정과 별개인 개발 fixture 경로이며, production signer/장치 권한을 자동으로 추가하지 않는다. fixture에 담기는 키와 계정은 테스트 전용이다.

S CLI 실행·서명·파일 전송의 자동화, 검토 실패 시 raw source 미리보기 확대, decision 이력 비교, activation/change plan 화면과 실제 현장 인수는 남아 있다. 첫 물리 셀은 NOT_COMMISSIONED다.
