# RX BehaviorTree.CPP execution nodes

Actual C++ nodes and factory integration for RXSequence/RXParallelAll/RXBranch/RXOperation/RXWait/RXIntervention. Uses C++17 and BehaviorTree.CPP4.8.3 commit `6e469c6ba133aaa842dac9b096b41f2d33ee2b0e`. The [official source](https://github.com/BehaviorTree/BehaviorTree.CPP/tree/6e469c6ba133aaa842dac9b096b41f2d33ee2b0e) and MIT license are included in the validation image's vendor tree.

Nodes do not contain device SDKs, ROS control, or P result persistence functions. A validated P client must supply Frames to Context, and a separate worker must handle Requests. **The actual P communication/state converter is not yet connected.**

## Execution boundary

- runtime.hpp/cpp: execution identity, immutable tick frames, operation/branch continuity checks, request queue.
- nodes.cpp: actual BT action/control. A tick reads the in-memory view and enqueues requests.
- xml.cpp: XML allowlist and resolved node/attribute/child-relationship validation before factory creation.
- tests.cpp: execution/rejection/restoration using synthetic P views and Rust compiler output.

One tick uses one frame. A Frame binds to run/executor session/resolved digest/visit/epoch. Checks include complete/current state, monotonic expiry, submission authority, and eligible nodes; authority and expiry are checked again when dequeuing. The client must build Frames from P's current state and deadlines. Arbitrary UI input must not be wired into these booleans/IDs.

Expiry blocks use of an old view; it is not evidence of physical stop time or remote completion. Wait also receives P's decision rather than producing success from a local timer.

## Node rules

- Repeated ticks do not recreate a Submit request for the same node.
- UNKNOWN/UNRESOLVED/integrity conflicts wait as RUNNING and are not reduced to ordinary FAILURE.
- Even after SUCCEEDED, handover is awaited if there is no release.
- Branch uses the recorded decision ID/selection. It rejects changes to existing selections, operation IDs, or terminal outcomes, and lost bindings in a complete view.
- Parallel suppresses new admission during failure, unknown state, or pending intervention. It does not treat an in-progress sibling as having completed native cancellation.
- Halt leaves a PauseExecutor request and stops new requests. It is not evidence of native cancellation, safe stopping, or resource release.

An invalid frame stops the context and requests pause. There is a queue of 32 ordinary requests and 1 separate pause request. Context identifies requests by run/node/visit/kind. The P client must bind this to normative keys/activations/slots and retrieve an uncertain send or lost response as the same request. Coordination of durable keys/checkpoints across process restart remains future work.

## XML validation

Checks one root/one BehaviorTree, exactly 6 RX node kinds, ID, binding/condition/procedure/timeout, child order, and the complete node list. Script, pre/post conditions, includes, arbitrary builtins, extra attributes, and duplicate nodes are forbidden. Registry and XML must come from the same validated resolved artifact.

## Build and tests

Prepare the exact commit in `dependencies/behaviortree_cpp.repos` at `vendor/BehaviorTree.CPP`. Vendor is an unchanged source cache.

```text
python3 tools/test_bt_executor.py --evidence-dir OUTPUT_DIRECTORY
```

The tool checks the commit and absence of source changes, then builds the executor-validation Docker target. Tests run with network none/read-only/cap-drop all/no-new-privileges and a read-only fixture mount. This is a **validation target, not one of the two product images**, and excludes device-specific ROS stacks, device permissions, and site startup.

Validation covers four scenarios in the actual BT engine (sequence/handover, branch/wait/intervention, parallel unknown state/authority withdrawal, XML/queue limits) and the 5-stage example generated by Rust. P frames, completion, and clearance are synthetic fixtures. Do not describe this as validation of actual P gRPC mapping, resident image operation, or device qualification.

## Next integrations

P run/checkpoint/branch/visit eligibility, exact protocol-to-Frame conversion, request receipts and durable key retrieval, journal reconnection, process supervisor, and operator UI must be connected. Context does not create P's explicit restart authorization itself. The Host continues to own native control and latest-sample/deadman handling.

The typed Frame from the P → S read client and the [source clock/IPC boundary](FRAME_BOUNDARY.md) are now connected. The S worker and durable request keys are connected for finite operations. The complete daemon, remaining mutations, and explicit restart/clearance remain future work.

The persistent executable is `rx-bt-engine`; initialization, STEP, HALT, CLOSE, and clock/IPC/parent-loss rules are documented in the [persistent engine specification](PERSISTENT_ENGINE.md). `rx-bt-engine-fixture` is restricted to test-harness builds.
