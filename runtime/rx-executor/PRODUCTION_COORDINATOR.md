# Serial material coordination and completion confirmation

SerialProduction mode processes materials in order within a run authorized by P. It connects admission of the first/next material, BT execution for the visit, P completion confirmation and preparation of the next context. ManualVisit mode still processes only the designated visit. CLI Options default to SerialProduction; setup/operation-count work uses ManualVisit.

## State ownership

P Production.Inspect provides consistent state readable before the first part and after final completion. It binds run/checkpoint, the full part list and each revision/disposition, budget, caller/session/cell epoch/scope and a bounded time interval to the same control cut. S validates bytes/hash/size/schema, original checkpoint artifact, actual cell/recipe, part ID/ordinal and budget consumption.

P's part list preserves ordering and IDs. Changed values at the same revision or a changed ID for the same logical material are not accepted. material_id is not arbitrarily generated. Actual material identification/genealogy remain a separate incomplete scope.

## Flow for one material

1. If an unfinished IN_PROGRESS material exists, retrieve its ID/ordinal. If uncleared material exists in another state, do not automatically create new material.
2. If the next material is needed and current P admission/remaining budget permit it, use frozen Cell.BeginPartAttempt.
3. S stores the expected ordinal and full body/key in the journal, records ENTERED and then transmits. P creates the actual part and consumes budget once.
4. BT/worker for that visit operate under the existing execution contract. C++ SUCCESS alone does not mark a part complete.
5. After reconfirming P's process frontier completion, S requests Production.CompletePart. P rechecks current authority, run/part CAS, actual results of the selected process and handover evidence.
6. Once a new P query confirms CONFIRMED_COMPLETED for that part, retire that exact context. Prepare the next material afterward.

P's `complete_part_transition` is shared by existing internal completion and the new API. Part disposition, run revision/checkpoint, mandate exhaustion, event and original response share the same commit. When all materials are complete and budget remaining is 0, the run becomes COMPLETED. Completion or repeat requests do not refund budget.

## Response loss and identical requests

BEGIN_PART/COMPLETE_PART use logical stages distinct from node execution requests. An identical unresolved body may use only its original key; a new CAS/key with the same meaning is allowed only after definitive atomic revision rejection.

If P queries already show the material, record its existing ID as an observation. Do not fabricate a missing RPC response. Completion responses are recovered in the same way. Reject a different part ID in a late response, different state at the same revision, or the same key with a changed body. Repeated completion requests for an already completed part create no new revision/event/budget change.

## Context retirement differs from stopping

Only an authenticated current P query can create a CompletedVisit value. EngineProcess.retire compares that value's run/session/recipe/visit/epoch with the current planner. Only a match allows cleanup of that planner without forwarding the run-pause proposal generated by CLOSE. This path must not replace a planner without confirmed part completion.

A new part uses a new BT context while retaining the run's current session/epoch/mandate. The final context is also retired after P completion confirmation. If the entire run is COMPLETED in P, service stop reason is COMPLETED and completion observation is preserved without a separate pause mutation to P. User stop, errors and new sessions/epochs follow the existing stop lifecycle. A previous execution generation is not converted into authority for the next part.

## Communication and support scope

Additional APIs are pinned through a [separate production binding](https://github.com/jack0682/rx-platform/blob/codex/initial-draft/spec/production/v1/README.md). base/cell and existing executor-read/prepare bindings remain. BeginPartAttempt's cell revision is in CellCall.expected_cell_revision; complete run/part revisions are in the body.

Two-consecutive-material integration has 3 cases: normal, first Begin response loss and first Complete response loss. Actual S service, persistent BT and P mTLS/SQLite handle part admission/completion/next context. The fixture synthesizes Host completion and three handover evidence items as inputs. It does not release before S requests a handover query. Checks confirm 2 P budget consumptions, 2 parts, 2 operations, 2 planner instances, no intermediate pause, PENDING preservation for lost replies and 0 additional planners after restart. Actual simulated Host/native delivery remains a separate existing integration-test scope.

This change provides serial material coordination. Parallel material pipelines, actual material genealogy, explicit restart/rebind with new sessions, setup completion coordination, intervention/clearance/cancel/control-session, large-run paging/indexes/capacity, full supervisor/product image and actual equipment acceptance remain outstanding.
