# Protocol-guarded Host and Executor recipes

`ProtocolGuardedService` classifies software bootstrap/cooperative shutdown for release-catalog-pinned `rx-hostd run` and `rx-executor-service cell run`. Site plans specify no effect, executable, argv, environment variables or status paths. Existing NonActuating/SoftwareOnly and RequiresPlatformAuthority meanings are preserved. GuardedServices permits only cooperative requests for the new classification and creates no physical lifecycle permission.

Optional `services` in startup configuration is a named map. Each entry contains `configuration:{path,sha256}` and a typed `scope` from the common status crate. Host scope is HOST/installation/host/installation_identity; Executor scope is EXECUTOR/installation/cell/service_journal(UUID)/configuration_digest. Names are flat labels of at most 64 alphanumeric/underscore/hyphen characters; the release generates `rx/service/<name>` program IDs and actual binary/init/run/effect. Names/scopes cannot supply arbitrary executables. These are deployment data-pin inputs, not UI/P operation inputs. Existing startup v1 without services remains supported.

The builder compares Host installation identity and Executor normalized configuration digest from actual pinned config bytes, and checks Host Bindings, Executor cell/definition and separate data/runtime roots. Initializer/daemon executables are restricted to runtime-inventory-pinned `/opt/rx/bin/rx-hostd` and `/opt/rx/bin/rx-executor-service`. Both programs' arguments maps are empty; sites cannot insert extra arguments. Each daemon still runs its original strict loader, TLS validation and backend/journal/current-authority checks. Composition projection checks do not replace them.

Multiple Hosts, Executors and cells are supported within the existing Plan limit of 32 processes. Each selected service binds to only one process; configurations in which separate processes with the same installation/principal revoke each other's sessions are rejected. Hosts may provide Bindings for multiple cells. Each Executor must match the definition of every selected Host providing the same installation/cell and directly depend on those Host process IDs. Executor configurations with no corresponding managed Host are unsupported in this composition. If optional status-http is selected, each Host depends on the status processes so diagnostics do not disappear first during shutdown. This is not a P-wide one-Run-per-cell constraint.

## Explicit initialization and startup

`rx-solutionsd init CONFIG` executes selected services' metadata initializers in topological order. Commands are restricted to fixed role-specific Host init or Executor cell init. Under supervisor state, `initialization.db` retains resolved plan/initializer-list/order digests and each step's program/role/instance and Pending/Entered/Completed/Failed. It commits Entered before crossing the OS execution boundary. An identical already Completed step is retrieved; Entered/Failed steps are not automatically re-executed. Completed is recorded only after actual initializer exit0 observation. After 30 seconds or a stop request, it requests TERM once from its owned child leader and retains the handle until actual exit. Force kill or timeout is not used as a successful result.

`run` requires the initialization journal and verifies that all steps with exact digest/list/role/order are Completed. Partial completion does not start services. Missing initialization files/records are not replaced by new init. It then uses the existing Supervisor Prepared→SpawnEntered→owned Child boundary. Host/E required-open independently rejects actual data loss/corruption again. If supervisor commit response is uncertain after successful child init, an original Completed record can be recovered; if only Entered remains, separate installation inspection/recovery is currently needed. An API to reconcile that state through stop seal/installation readers remains future work; a new ID or init replay cannot bypass it.

Initialization and supervisor stores must not overlap daemon data roots. `/run/rx-solutions` must be provided as an actual writable runtime directory. The current image's `supervise CONFIG` is the run path; init explicitly invokes `/opt/rx/bin/rx-solutionsd init CONFIG`. Existing software-only `inspect/run/activate` and configurations are preserved. `activate` applies only to existing non-actuating plans and does not automatically approve guarded restart.

## Current instance observations

Uses guarded status from shared `rx-service-status`. Release base path `/run/rx-solutions/<service-name>.json` derives `<service-name>.<instance UUID>.json` for each launch. The manager supplies existing RX_PROCESS_INSTANCE_ID together with new RX_PROCESS_STATUS_PATH. It neither deletes old files nor overwrites foreign-owner state.

The reader checks scope/instance/owned PID, file type/size, Linux clock and source age of at most 2 seconds. The backend rejects same-instance sequence/time regression or changed payload digests at the same sequence. Original observation time and digest are preserved. AliveOnly or another HTTP response in Starting does not count as guarded readiness. Observation continues after Ready; loss of protocol readiness connects to the composition's cooperative shutdown latch. Ready is software protocol state, not RunMandate or physical control readiness.

The resident cell executor continues providing the protocol during internal RunService completion/planner cleanup. Internal work Stopping/Stopped is not reported as daemon-wide Stopping. Explicit cell-service stop requests, overall Stopped and Attention are reflected separately; after normal completion, the same executor returns to Idle and waits for the next work.

## Shutdown and evidence

Protocol-guarded children have automatic restart0, and the backend also rejects force kill. Existing process-group signal policy for ordinary software recipes is retained, but Host/Executor receive TERM **only on positive leader PIDs**. Thus the supervisor does not terminate Host child bridges/controllers or Executor planners first. Each daemon checks adapter safe-to-drop and actual planner cleanup through its existing path.

Shutdown dependency order is Executor → Host → optional status. Permission to request cooperative shutdown differs from confirmed safe-to-drop/shutdown completion. If the Host cannot obtain support/residual-command evidence, it retains its existing owner and the supervisor keeps waiting. TERM requests do not require safe-to-drop to be established beforehand.

If TERM delivery fails, retain the same owned child and retry the cooperative request. Record successful transmission and start waiting only after actual delivery succeeds. Metadata initializers follow the same principle: timeout or failed signal commands are not converted into successful shutdown.

OS exit is Exited; new `guarded_exit` is separate. Confirmed requires both current-instance Stopped metadata and owned-child exit0. Missing/stale/different-instance metadata, Ready/Attention or exit1/signal termination are Unconfirmed. Original observation time/digest/sequence and reconciliation_required are preserved; after a local exit-record commit failure, the same owner reuses the exit fact it already observed. Metadata is not refreshed to a new timestamp. An unexpected guarded-daemon exit latches cooperative shutdown of the remaining composition without automatic restart.

`all_exited` is an OS fact. The daemon CLI returns overall shutdown success only when `guarded_shutdown_confirmed` is separately true. Even confirmed shutdown preserves remaining evidence/attachments as `reconciliation_required`. Neither boolean nor child exit is reinterpreted as physical qualification, work outcome or native support proof. Actual Host proof inspection/sealing remains inside the Host. This procedure is not claimed to prevent external container-runtime SIGKILL or power loss.

Initial image acceptance uses FILE_SIMULATION Host and the existing P–S flow. Dedicated catalog tests for the same structure cover 2 Hosts/2 Executors/2 cells, their dependencies/definitions and duplicate-principal rejection. Initializer tests also cover completion/retrieval of 4 named steps and prohibition of partial/Entered replay. Physical ROS JTC provider/device-driver lifecycle, explicit reactivation of guarded plans, managed recovery of initialization Entered states and log/status-history retention/rotation remain future work. Additional test sources cover alive-only bypass, restart/arbitrary-argument rejection, isolated instance paths, Ready loss, exit/final-report combinations, prohibition of force after timeout and the counterexample in which TERM must not reach the actual child group. Build/test results follow the parent verification record.
