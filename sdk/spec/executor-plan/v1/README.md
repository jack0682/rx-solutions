# Optional executor state preparation binding v1

`rx.executor.plan.v1.ExecutorPlanService.PrepareCheckpoint` prepares complete typed successor state for the frozen `Workflow.CommitCheckpoint` RPC. It does not apply a branch, start an authoritative wait, allocate a child operation or grant actuation permission. Base/cell v1 negotiation and current executor authentication/assignment are mandatory. This optional binding is checked separately and does not replace either frozen manifest or the optional executor-read binding.

The request carries a positive visit, resolved node identity, action (CHOOSE_BRANCH/START_WAIT/CHECK_WAIT), and the canonical SHA-256 of binding.json. Its CallContext has neither expected_revision nor request_key. Preparation can store immutable artifacts but does not change RunView.revision. Repeating a still-valid preparation with unchanged P state/evidence reuses the same candidate. Missing/unknown condition evidence returns WAITING without choosing a branch. Existing committed decision/window returns ALREADY_APPLIED. These two states carry current expected_revision and no checkpoint/timestamps.

READY carries expected_revision, complete Checkpoint at expected_revision+1, P-issued prepared_at and valid_until. The payload is a full `rx.executor-state.v1` artifact with unchanged run metadata, budgets and activation/slot bindings, and one proposed process decision or wait transition. It is readable through the existing run-scoped artifact route. It is not a command envelope disguised as state. Arbitrary artifact upload is not provided.

Commit uses the exact frozen ChangeCheckpoint body: request key required, body expected_revision used, context expected_revision absent. P checks current access before key lookup; same committed key/body returns the original RunView. A new commit checks run CAS, current execution authority, proposal session/boot/epochs and expiry, exact artifact/schema/size/activation mapping, and freshly re-derives the successor from current P facts. State, run revision, control record and exact reply commit together. Caller-supplied outcomes, branch verdicts, clocks or child IDs cannot replace P's stored proposal and evaluation.

The preparation window is at most 100ms of the trusted P clock. A wait's start/deadline use its original P preparation time and become authoritative only on successful commit. A committed window cannot be restarted. A satisfied wait candidate cannot commit at or after its deadline; P then prepares a timeout candidate. Condition/source changes can reject a candidate even if run revision is unchanged. EXPIRED and STALE_REVISION are re-preparation conditions for this atomic commit; ordinary transport failure does not establish non-commit.

Current preparation scope is finite process branch and wait transitions. Intervention/clearance, arbitrary third-party executor schemas, long-run storage capacity, proposal retention and production supervision are not completed by this binding. Tests use explicit simulation conditions and do not qualify a physical cell.

## Confirmed rejection metadata

Only Workflow.CommitCheckpoint atomic STALE_REVISION/EXPIRED rejection carries a single `rx-checkpoint-error-bin` binary metadata value: strict frozen ErrorDetail protobuf, at most 1024 bytes. REVISION_CONFLICT/REFRESH must pair with gRPC ABORTED; EXPIRED/RECONCILE must pair with FAILED_PRECONDITION. All optional ErrorDetail fields and Reason.detail are absent, related_ids empty. This is separate from standard grpc-status-details-bin. No human-readable text is a retry signal. Duplicate, malformed, unknown or mismatched metadata, bare ABORTED/FAILED_PRECONDITION, and transport errors do not prove non-commit. After a confirmed rejection the executor refreshes current P state and prepares a new candidate; it never blindly changes only the key.
