# Host rejoin context, scoped recovery communication — candidate v1

Status: candidate, not published or a physical continuity qualification.

This candidate records an authenticated Host incarnation replacement and exposes local read prerequisites. A separate proposal endpoint performs a bounded pinned read. Neither endpoint acquires a grant, replaces a registration, concludes an operation, releases resources, qualifies or Arms a cell.

The producer-opening transaction records an immutable `rx.host-invalidation-origin.v1` when an existing authenticated producer reports a different boot and actual Host registrations are affected. The record binds installation/store generation, previous/current Runtime, old/new producer session/boot/evidence journal/authentication binding, prior registrations, the full affected cell cohort, exact configuration/epoch/scope before/after boundaries and only each newly created DeviceRestart restriction. Existing restrictions must remain unchanged. The new session, invalidations and origin commit atomically. An identical reconnect recovers the same session and origin. Missing legacy provenance is not reconstructed from a reason string.

GET `/api/v1/host-rejoin-context?host=...&origin=...` requires a current terminal-mTLS ReleaseManager covering the complete prospective cell cohort. It checks access before exposing provenance. It returns a `rx.host-rejoin-context.v1` and `RX-HOST-REJOIN-CONTEXT-v1` digest, current producer, origin/digest, current cell cuts, retained normal-binding baselines and registrations, transport pin and explicit blockers.

`local_prerequisites_current=true` means only that the local records match at this read cut. The context includes the current shared clock ID. `fresh_host_read_required` is always true and `operation_authorized` is always false. Registration/grant values in this response remain historical data, not usable operating authority. This endpoint does not create an approval or recovery binding.

POST `/api/v1/host-rejoin-proposals` accepts only an idempotent request key plus host/origin, expected context digest and complete expected cell revisions. The release-configured worker recovers an existing proposal before new network I/O. Otherwise it checks current writer authorization, uses the deployment-owned TLS pin/endpoint, opens only declared configuration cells, and obtains actual configuration/source snapshots. Callers cannot submit a snapshot, endpoint, certificate, path or RPC method.

The writer repeats current actor and exact context checks after I/O. It verifies the replacement Host boot, retained delivery/evidence journals, old source generations, current schemas/units/quality/age, resource fence counters, known pending operations/permits and retained configuration application proof. The old configuration receipt remains attributed to its original Host boot; it is not rewritten to the new boot. Each read window and its age at acceptance are bounded by the existing 100ms recovery-read limits.

A successful proposal stores immutable context/read evidence and attribution in `rx.host-rejoin-proposal.v1`. GET `/api/v1/host-rejoin-proposal?id=...` requires current terminal/full-cohort access. `context_current` includes the 30s proposal lifetime; `read_current` additionally checks the original observation's freshness now. Expired observations are still historical data. Original-key recovery returns the same proposal without refreshing its evidence, even if that evidence is no longer current. `operation_authorized` remains false. No approval or Fence is performed by proposal creation.

The first supported local comparison requires the same Runtime, unchanged authentication/evidence journal, exact cohort/configuration/revision/epoch/scopes/restriction, unchanged prior registration, matching immutable baseline identity and currently configured transport, and negotiated cell definitions on the replacement producer. Current active Run/mandate/permit, missing origin/baseline/transport, foreign or changed context remain blockers. Journal ID equality does not prove prefix completeness or native-device continuity; fresh endpoint, configuration, source-generation and fencing checks are explicit steps. Receipt lookup is correlated evidence; full prefix completeness and native continuity qualification are still not inferred.

The existing P-Runtime-restart/retained-Host recovery API retains its meaning. No RuntimeRestart origin is fabricated for a Host restart. Multiple unbound Host replacements, compound Runtime/Host changes and legacy unowned restrictions are not silently promoted. Known-result settlement is an explicitly approved separate step below. Normal rebind is an explicitly approved separate step below. Fresh qualification/next job remains a separate obligation. Scoped recovery communication does not complete those responsibilities.

Compatibility: candidate revision2 adds a shared clock field, proposal read/creation endpoints and proposal records. Base/cell protobuf numbers and manifests are unchanged. A changed context digest requires a fresh context read. The SDK exports this candidate specification; application authority remains excluded. There is no implicit migration or deletion of old records.


## Scoped approval, Fence and query

New proposals include optional `recovery_scope`, fixing the original entered operation/permit/intent/profile/journal/invocation/message identities. Older proposals omit this field, retain their canonical digest, and remain read-only; approval refuses a missing scope. Older strict clients must be updated to consume the new optional field. The base/cell wire is unchanged.

POST `/api/v1/host-rejoin/approve` takes an idempotent mutation containing the proposal ID, revision, digest and exact cell revisions. A current terminal ReleaseManager covering the full cohort must approve the unchanged context within the proposal's 30s lifetime. The original operation scope is checked again. One current recovery binding owns the Host; another proposal cannot replace it while its approval/context remains current. The immutable proposal is never rewritten.

Approval stores a `rx.host-rejoin-binding.v1` in FENCING with exact per-cell Fence requests. It does not require the old observation to remain younger than 100ms. Before every send, the restricted worker obtains a new actual pinned read and the writer rechecks current approval actor, cohort, context and freshness. Entered requests are persisted before I/O and retain their IDs after reply loss. Matching pending Fence outbox entries are reused only when the whole body is exact and the candidate is unambiguous. No grant, Arm, Prepare, Authorize or native operation replay is available through this worker.

An acknowledgment must match the entered request/body, current replacement Host boot and retained journal. A correlated late acknowledgment remains recorded after authority/context loss but leaves the binding at ATTENTION. Only all-cell acknowledged fencing plus another actual read showing the exact fenced epoch/scopes/blocks can reach RECOVERY_ONLY. The normal Host registration and old baseline are untouched; RECOVERY_ONLY is restricted communication, not operating readiness. `operation_authorized=false` remains mandatory.

GET `/api/v1/host-rejoin-binding?id=...` reports current access/approval context and read freshness separately. POST `/api/v1/host-rejoin/progress` accepts only the existing binding ID and continues those exact approved tasks. A transport outage after approval may leave FENCING; original approval request recovery or explicit progress continues it without inventing a new request ID. Current actor revocation/context drift blocks later sends; previously correlated facts are retained.

POST `/api/v1/host-rejoin/query` accepts an existing binding ID and one operation from its immutable scope. Fresh actual reads and current writer checks precede receipt query and lookup. Correlated receipt/native facts are recorded in `rx.host-rejoin-query.v1` plus a raw audit event. Missing/unavailable/unsupported query results are not absence or failure proofs. Filtered evidence is not ingested as a producer prefix, and `evidence_complete=false`. This slice neither mutates Work nor promotes outcomes nor releases resources. `context_current_at_record` distinguishes late evidence from currently authorized communication. Raw result continuity and physical support must still be qualified before settlement/rebind.

Compatibility: candidate revision3 adds the optional recovery scope and new binding/query records/endpoints. It preserves old proposal digest encoding when scope is absent and never approves an old unscoped record. No record is silently upgraded; no product key or running installation migration is performed by this candidate.


## Known-result settlement after rejoin

POST `/api/v1/host-rejoin/settle` accepts an idempotent mutation containing `reference: {binding, query}` and `settlement: {operation, expected_operation, expected_cell, justification}`. It accepts no observations or endpoint. The current terminal ReleaseManager must cover the whole binding cohort. The original work must be a confirmed successful finite action, valid and quarantined, with a consumed old permit, revoked/inactive mandate and RecoveryRequired run under the unchanged configuration. Only the exact replacement DeviceRestart restriction and permitted AuthorityRevoked restrictions are eligible; unrelated holds are not adopted.

The selected query must belong to the same approved binding/operation and have been current when recorded. Its ResultCaptured receipt must match original intent/invocation/journal and cannot precede a known receipt sequence or conflict at the same sequence. Its native evidence set must exactly match all native evidence referenced by the already-confirmed work, including native/device identity and captured values. This is per-operation continuity anchoring, not a claim of complete Host journal-prefix preservation or physical correctness.

Approval persists a current 30s settlement authorization with an optional rejoin reference in the existing settlement ledger. The historical permit/normal registration are not rewritten. The restricted worker obtains current handover observations and a fresh pinned snapshot; the writer rechecks both approvals, exact context, source identity, current resource fences and authorization lifetime. The shared handover validator requires all three no-pending/control/support predicates, correct original invocation/profile/device session, the replacement Host boot, quality, bounded age and capture ordering. Only then are resource custody and the operation released and existing part/run completion rules evaluated. A current reconciliation request for that work is marked complete without dispatching new work.

The original-key retry returns the current durable authorization and performs no further Host I/O after it was applied. Normal settlement APIs reject a rejoin authorization; this path uses a typed internal actual-read proof and never constructs a fake Host registration or caller-supplied Host identity. Old authorizations omit the optional rejoin field and retain their semantics. Strict old readers of new authorization records require an upgrade. Candidate revision4 documents this additive record/API change; base/cell wire numbers are unchanged.

Successful settlement is not normal rebind, qualification or next-job authority. Unknown outcomes, different native-device generations, rollback without retained operation anchors, partial effects and unrelated restriction causes remain unsupported by this step.


## Explicit normal rebind after closed responsibilities

POST `/api/v1/host-rejoin/rebind` accepts an idempotent mutation containing the recovery binding ID, expected binding revision, immutable proposal digest and exact cell revisions. Approval requires current terminal ReleaseManager access for the entire cohort, the current recovery approval/context and all affected work/resources/run recovery responsibilities closed. This candidate supports disjoint per-cell Host resource sets; overlapping lease scopes are rejected rather than split or fabricated.

The approval has a 30s execution lifetime. A release-configured worker obtains new pinned reads and prepares one immutable request plan per Host cell using deployment-owned TTLs. It reserves increasing resource fence counters, retaining the old Host registrations and `host-link-current` pointers until final commit. Preparation and each grant send are durable. Fresh reads accept only the recorded previous resource counter before send, or the exact reserved counter after a send was entered; unrelated counters or a replaced reservation are rejected. The current correlated J3 cell Fence acknowledgment is reused only with an actual read confirming its exact epoch/scopes/blocks. A separate grant-capable rebind wrapper exposes only AcquireGrant; ordinary RestrictedHost remains unable to acquire grants or admit work.

Original grant request IDs and conservative send times survive reply loss. Every response must match the actual replacement Host boot, owner, resources, fence and TTL. A late correlated response is retained without adopting the Host after context/authority loss. All grants plus a final fresh complete read are required before one transaction replaces every affected Host registration, publishes all new current link pointers and creates immutable normal-binding baselines. Partial responses cannot activate a subset. Normal PrepareHostLink/CommitHostLink retain their changed-incarnation rejection; no old guard is disabled.

GET `/api/v1/host-rejoin-rebind?id=...` and POST `/api/v1/host-rejoin/rebind-progress` inspect or continue the existing approval. A BOUND receipt is historical completion; `production_authorized=false` always. `current` describes the locally matching binding identity, not physical readiness. Prepared step plans retain their issued command snapshots; current normal plans and registrations are stored separately. An expired or abandoned entered grant requires further explicit resolution; this revision does not silently create a new request ID or steal a prepared approval. No general liveness claim is made for expired/partially acquired rebind attempts.

A retired ConnectionService polls only for a committed matching rebind of its exact retired producer session/cell. It then re-enters its normal pinned bootstrap and starts the normal observation, delivery, configuration and qualification workers. No marker means no adoption or grant. Unrelated failures still retain their prior fatal behavior. The marker does not qualify or Arm the cell, clear restrictions, restore old mandates or permit next production.

Each new baseline has an immutable `rx.host-rebind-configuration-origin.v1` relation to its prior baseline/digest and approved rebind. Configuration proof validation follows only a matching committed relation, checks the recorded proposal/plan/cohort identities and pinned source attributes, and validates the original configuration receipt against its original Host boot. It does not rewrite old receipts. The chain is bounded to 64 links; missing, changed or cyclic history is refused. New configuration applications use their own proof instead of borrowing the old link.

Candidate revision5 adds rebind plans/receipts/history and endpoints. Base/cell protobuf numbers and manifests are unchanged. Current physical support, multi-owner shared resource leases, expired partial-grant resolution, full journal rollback and fresh qualification/next-job verification remain separately bounded obligations.


## Review-bound DeviceRestart clearance

GET `/api/v1/host-rebind-restrictions?cell=...` requires current terminal ReleaseManager access and full shared recovery-cohort access. It returns eligible immutable `Restriction` references and `restriction_digests` keyed by block ID. `clearance_authorized=false`: discovery is neither clearance nor qualification. Each reference binds the exact DeviceRestart block/cell/Host, authenticated replacement origin/digest, the completed rebind which covered it, the currently matching normal rebind/baseline, and unchanged configuration. A bounded verified baseline/rebind chain can cover earlier completed replacements; reason names, missing legacy origins, uncommitted rebinds, changed configurations and unapproved subsequent Host boots do not qualify.

The existing qualification-review Begin accepts an optional `host_rebind_restrictions` map of block IDs to those exact digests. Selecting any references creates `rx.requalification-request.v3`; v1/v2 cannot carry them. Empty maps/vectors remain omitted from canonical encoding, preserving historical request digests. The complete selected references are included in the request and therefore in the signed report/decision scope, alongside any runtime restrictions. Selection repeats current normal-binding identity/configuration and complete caller-scope checks before invalidating for review.

A `rx.host-rebind-restriction-binding.v1` record binds each selected restriction to that review ID, Change, cell, request digest and restriction digest in the same transaction. It does not assign a permanent Change owner or clear the block. Issuance and activation require the currently matching request/normal rebind basis and this exact review-bound record. A DeviceRestart clear request from another review, without a selected reference, or with changed source/history/configuration is refused. Other reasons keep their existing ownership rules; unrelated holds are not adopted. No RuntimeRestart origin is fabricated.

Actual clearance still requires a verified signed six-area report, current review decision, current issuer/CAS, confirmed fencing, real current Host qualification acknowledgment and the existing final activation transaction. Rebind completion by itself remains non-production-authorizing. Revoked run/mandate/permit identities are not restored; any next job needs a distinct current execution authorization.

Candidate revision6 adds the optional Begin/request field, the explicit v3 request schema, read endpoint and review-binding records. Existing v1/v2 request canonical bytes remain unchanged when the new field is absent. New strict clients/fixture signers must understand v3 before reviewing its signed reports. Base/cell protobuf numbers and manifests are unchanged. This revision does not establish arbitrary configuration transitions, compound P/Host restart, physical qualification or expired partial-rebind recovery.
